# Serialization boundaries: the Rust↔TypeScript wire

## The diagnostic order (always)

When a serialization error appears at the boundary — msgpack decode failures, "invalid type" errors, unexpected `null`/`None` deserializations, "unknown variant" errors — your first instinct is almost certainly wrong. The default order of suspects is:

### 1. The Rust side hasn't been recompiled

The most common cause. The user changed a Rust type, the wasm wasn't rebuilt, the conductor is serving the old wasm, and the TS side is now seeing wire data from the *old* shape. Symptoms: errors that mention fields that don't exist anymore, or fields that *do* exist but with the wrong type.

**Fix:** rebuild the wasm and reload the conductor. In a nix-flake project: `nix develop -c cargo build --release --target wasm32-unknown-unknown` (or whatever the project's build script does), then restart the conductor.

### 2. Rust type and TS type have drifted

The second most common cause. Adding a field to the Rust struct doesn't automatically update the TS type. Renaming a field with `#[serde(rename = "...")]` on the Rust side requires the TS side to use the new name. Adding `#[serde(rename_all = "camelCase")]` changes the wire format for *every* field. Adding `#[serde(tag = "type")]` changes how enums serialize.

**Fix:** check the serde attributes on the Rust side, then check the TS type definition for matching field names. In a `zits`-codegen project, re-run the bindings script (`nix develop -c bash scripts/ts-bindings.sh` or whatever the project uses).

### 3. Wrong-side check

The third most common. Sometimes the agent has been inspecting the TS side for a bug that's actually on the Rust side, or vice versa. If the error message contains the wire bytes (msgpack hex or similar), decode them by hand and check what they actually look like — that tells you which side is producing the wrong shape.

### 4. (Essentially never) msgpack or serde version mismatches

**In real-world projects this is almost never the cause.** The only documented case where it actually mattered: a project's `package.json` had been generated by an LLM that picked an obsolete `@msgpack/msgpack` version that disagreed with what `@holochain/client` ships internally. The fix in *that one specific case* is to align with `@holochain/client`'s internal version (run `npm ls @msgpack/msgpack` to see what's in the dependency tree) — **not** to bump arbitrarily.

If a human developer hand-wrote the project's `package.json`, you are almost certainly chasing the wrong cause. Walk back to step 1 and re-check whether the wasm actually got rebuilt.

Don't pin or bump `rmp-serde`, `serde`, or `@msgpack/msgpack` versions as a first-line fix. This is the Claude reflex from Tripwire E in the main SKILL.md: it wastes hours on a phantom cause. Only consider it if you've exhausted #1, #2, #3 *and* you have positive evidence (a release note, a bug tracker link, or the LLM-generated-package.json scenario above) pointing at a version-pin issue.

## The default serde enum shape pitfall — named, with named fixes

Rust enums like:

```rust
pub enum Status {
    Online,
    Offline,
    Away,
}
```

serialize via Holochain's msgpack path to **`{Online: null}`-style variant-object tags** by default. The TS side sees `{Online: null} | {Offline: null} | {Away: null}` instead of the bare strings `"Online" | "Offline" | "Away"` you'd expect from JS conventions.

This pitfall has been independently rediscovered multiple times. There are three known fixes, all valid:

### Fix 1 — Embrace the variant-object shape on the TS side

Vines does this. The TS side accepts `{Online: null}` as the wire format and uses wrapper class instances (`StatusMat` or similar) that materialize the wire shape into a more ergonomic interface internally. No Rust-side changes; the TS just learns to handle the default shape.

This is the simplest fix if you're already using a materialize/dematerialize layer (which `zits`-codegen projects need anyway because hashes become `Uint8Array`).

### Fix 2 — `UIEnum(pub String)` newtype with custom serde

Acorn's pattern. Define a newtype:

```rust
#[derive(Serialize, Deserialize)]
pub struct UIEnum(pub String);
```

Then on the enum, use `#[serde(from = "UIEnum", into = "UIEnum")]` and write manual `From<UIEnum>` impls that translate between the enum variants and the bare strings. The wire format becomes a bare string, the Rust side still has typed enum values internally, and TS gets a string union.

Acorn uses this for `AchievementStatus`, `RelationInput`, `ComputedScope` (`projects_integrity/src/ui_enum.rs`).

### Fix 3 — Hand-rolled `Serialize`/`Deserialize` impl

Also acorn. For one-off cases, write a custom `impl Serialize for Status` and `impl<'de> Deserialize<'de> for Status` that emit/parse bare strings directly. More verbose than `UIEnum` but lets you handle edge cases like case-insensitive parsing.

Acorn uses this for `Profile::Status` (`profiles_integrity/src/lib.rs:82-107`).

**Important: never "clean up" hand-rolled `Serialize`/`Deserialize` impls** by replacing them with `#[derive(...)]`. They're almost always there to fix the default enum shape, and removing them silently changes the wire format. This is anti-pattern #11 in the main SKILL.md.

## Three serialization strategies for the Rust↔TS boundary

### Strategy A — Hand-mirrored TS types

The simplest. The developer writes Rust types and matching TypeScript types by hand. unyt-app, dino-adventure, and emergence all do this. No tooling.

**Pros:** simple, no build step, works with any project.
**Cons:** zero compile-time check that Rust and TS agree. Drift is silent until runtime.

### Strategy B — Hand-mirrored zod schemas, TS types derived

Acorn's pattern. The developer writes Rust types and matching **zod schemas** in TypeScript; the TS types are derived from the zod schemas via `z.infer<typeof FooSchema>`. Zod doubles as a runtime parser, so the TS side can validate incoming wire data and catch drift at runtime instead of crashing.

**Pros:** runtime validation of wire data; clear single source of truth on the TS side.
**Cons:** still no Rust↔TS compile-time check. Adding a Rust field still requires manual zod update. Two sources of truth (Rust struct + zod schema) that must be kept in sync.

### Strategy C — Codegen from Rust via `zits` (the default for new projects)

Vines's pattern, and the **recommended default for new Holochain projects**. `zits` (https://github.com/lightningrodlabs/zits) is a Rust binary that parses Rust source files and generates matching TypeScript bindings — types, function names, proxy classes — from `#[hdk_extern]` markers and `#[derive(Serialize, Deserialize)]` structs.

The output is six files per zome under a `bindings/` directory: `{zome}.types.ts`, `.fn.ts`, `.proxy.ts`, `.integrity.ts`, plus a shared `deps.types.ts`. Each file is marked "generated, do not edit manually." The user runs `bash scripts/ts-bindings.sh` (or equivalent) after every Rust type change to regenerate.

**Pros:** the only strategy where adding a Rust field flows to TS automatically. No manual mirror to maintain.
**Cons:**
- Hashes become `Uint8Array` aliases on the TS side (because that's what they are on the wire). The UI must wrap them in convenience classes (`ActionId`, `EntryId`, `AgentId`) via a materialize/dematerialize layer.
- Enums emit the default serde external-tag shape directly (so the UI sees `{Foo: ...}` variant objects). See "default serde enum shape pitfall" above for fixes.
- `#[feature(zits_blocking)]` is a *load-bearing pseudo-attribute* — it tells `zits` to use `callBlocking` instead of `call` in the generated proxy. It's not a real Rust feature gate. The crate-level `#![allow(ill_formed_attribute_input)]` exists to silence the warning. Don't "clean up" the allow.
- Some types (`XSalsa20Poly1305EncryptedData` in vines's case) degrade to `unknown` because `zits` can't model them. That's OK; treat them as opaque on the TS side.

**For Eric's projects specifically:** Eric is currently maintaining an updated fork of `zits` at `https://github.com/metacurrency/zits` (or wherever the fork lands). Once the fork is the source of truth, point new projects at it. For now, upstream `zits` is the default to recommend.

## Detect-and-stay-in-idiom

If a project already uses Strategy A or B, **do not migrate it to `zits` unilaterally**. The detect-and-stay-in-idiom rule applies. Strategy C is the new-project default; existing projects using A or B continue with their chosen approach unless the user explicitly asks to migrate.

To detect which strategy a project uses:
- Look for `scripts/ts-bindings.sh` or `zits` in `package.json` / `Cargo.toml` / `flake.nix` → Strategy C
- Look for `zod-models/` workspace package or zod schemas referenced from `package.json` → Strategy B
- Otherwise → Strategy A (assume hand-mirrored)

## Other things to know about the boundary

### Hashes-in-entries: bytes vs B64 strings

Two valid choices:

- **Raw `ActionHash` bytes inside entries** (most projects). Cheap Rust-side comparisons. Requires the UI to wrap hashes in convenience types.
- **`ActionHashB64` strings inside entries** (acorn). The UI can string-compare directly. Bakes a UI-friendly encoding into the DHT *permanently*. Rust-side hash math now requires a parse on every comparison.

Pick one and stay consistent within a project. Don't mix.

### `f64` vs `Timestamp` for embedded timestamps

- **`Timestamp`** (i64 microseconds, the HDK type). The UI handles bigint coercion.
- **`f64`** (acorn). JS-number-compatible. Loses precision past 2^53 microseconds; not Y2K-safe but probably fine for app lifetimes.

Don't silently convert one to the other across the boundary.

### `#[serde(rename_all = "camelCase")]`

Universal at the *struct* level in modern apps. Apply it on every entry struct that crosses to the UI. Crate-level application is unusual; vines deliberately leaves some inner structs in snake_case to be camelCased by `zits` codegen instead.
